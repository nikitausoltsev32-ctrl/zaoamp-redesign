## Причина: статика отдаётся без сжатия

Разбор `/catalog/kroshka/` mobile (худший результат, LCP 8,5 с):

| Тип | Запросов | Вес |
|---|---|---|
| **Script** | **22** | **818 КБ** |
| Font | 4 | 212 КБ |
| Image | 5 | 65 КБ |
| Stylesheet | 1 | 55 КБ |
| Document | 1 | 20 КБ |
| Третьи стороны | 0 | 0 КБ |
| **Всего** | 37 | **1211 КБ** |

Картинки — 65 КБ из 1,2 МБ. Оптимизация изображений тут ни при чём, она уже сделана
хорошо. **Проблема в 818 КБ скриптов**, и главное — почему их так много в передаче.

### Проверка заголовков

```
GET /_next/static/chunks/320-276eaaae858d2b08.js
  Content-Type: application/javascript
  Content-Length: 118765
  Cache-Control: max-age=31536000
  Content-Encoding: —          ← ОТСУТСТВУЕТ

GET /_next/static/css/c99485975da736ee.css
  Content-Length: 56133
  Content-Encoding: —          ← ОТСУТСТВУЕТ

GET /catalog/kroshka/  (HTML)
  Content-Encoding: gzip       ← есть
```

Запрос делался с `Accept-Encoding: br, gzip, deflate`. HTML сжимается, **вся статика —
нет**. Сервер `nginx/1.28.3 (Ubuntu)` отдаёт `/_next/static/*` как есть.

Это объясняет цифры: 818 КБ скриптов — это несжатый объём. При gzip/brotli на JS и CSS
типичное сжатие 3–4×, то есть **818 + 55 КБ → примерно 200–250 КБ**. Вес страницы падает
с 1,2 МБ до ~450 КБ, и это напрямую бьёт по LCP: на дросселированном 4G канал перестаёт
быть занят скриптами, пока браузер тянет LCP-элемент.

Косвенное подтверждение того, что дело в канале, а не в процессоре: TBT 12 мс при
FCP 3,3 с и LCP 8,5 с. Разрыв 5,2 секунды между первой и главной отрисовкой при
свободном главном потоке — это ожидание сети.

### Исправление

Включить сжатие статики на прокси. Для nginx:

```nginx
gzip on;
gzip_vary on;
gzip_comp_level 6;
gzip_min_length 1024;
gzip_types application/javascript text/css application/json image/svg+xml;
# и, если собран модуль:
brotli on;
brotli_types application/javascript text/css application/json image/svg+xml;
```

Файлы под `/_next/static/` иммутабельны (`max-age=31536000`), поэтому лучший вариант —
`gzip_static`/`brotli_static` с предсжатыми `.gz`/`.br` рядом с исходниками: сжимаем один
раз при сборке, отдаём без нагрузки на CPU.

### Но сначала: конфиг в репозитории не описывает продакшен

Это блокер для правки, и он важнее самой правки.

`docker-compose.yml` поднимает **Caddy** на портах 80/443 с проксированием на `app:3000`,
а `Caddyfile` содержит:

```
amp-minerals.ru, www.amp-minerals.ru {
	reverse_proxy app:3000
	encode gzip zstd
}
```

То есть по репозиторию сжатие **включено**. А живой сервер отвечает
`Server: nginx/1.28.3 (Ubuntu)` и статику не сжимает.

Значит продакшен работает не по этому docker-compose: перед приложением стоит nginx,
конфига которого в репозитории нет. Отсюда два следствия:

1. **Правку сжатия надо делать в конфиге nginx на сервере, а не в `Caddyfile`.**
   Изменения в `Caddyfile` на продакшен не повлияют вообще.
2. Ровно то же касается остальных серверных задач из плана: 301 с www, security-заголовки.
   Я ранее указывал для них `Caddyfile` — это была ошибка, цель — nginx.

Кстати, это же объясняет и `www → 200` вместо 301: в `Caddyfile` оба хоста обслуживаются
одним блоком без редиректа, и nginx, судя по поведению, настроен так же.

**Первым делом надо выяснить, где лежит рабочий конфиг nginx** и привести репозиторий в
соответствие с реальностью — иначе любые инфраструктурные правки уходят в пустоту.

**После этого сжатие — самая дешёвая правка во всём аудите: несколько строк конфига,
эффект — LCP с 8,5 с до ориентировочно 3–4 с на всех страницах сразу.**

## Второе по значимости: неиспользуемый JavaScript

Lighthouse: **225 КБ лишнего JS** (экономия ~1200 мс) и 39 КБ лишнего CSS (~150 мс).

| Чанк | Всего | Не используется |
|---|---|---|
| `320-276eaaae858d2b08.js` | 115 КБ | **68 КБ** |
| `293-f9a0970778a25a67.js` | 57 КБ | **50 КБ** |
| `cfeffc86-78be86841cc89ca1.js` | 168 КБ | **50 КБ** |
| `452-9fb5b6d7da0c4d0d.js` | 109 КБ | **34 КБ** |
| `495-fa53de244435748c.js` | 31 КБ | **23 КБ** |

`293` используется на 12% — почти целиком лишний на этой странице. Кандидат на
`dynamic()` c `ssr: false`.

Что в тяжёлых чанках, видно из `next.config.js`:
`optimizePackageImports: ['framer-motion', 'lucide-react']`. **framer-motion** —
основной подозреваемый на `cfeffc86` (168 КБ, из них 50 КБ не используются).
`optimizePackageImports` сокращает импорты, но саму библиотеку из бандла не убирает.
Для страницы каталога, которая на 95% статический контент, анимационная библиотека
такого веса — явный кандидат на `dynamic()` или на отказ в пользу CSS-переходов.

Плюс `polyfills` 91 КБ грузится всем: проверить `browserslist`, при отсутствии IE11
в таргетах полифилы отключаются.

## Третье: шрифты

212 КБ в 4 файлах — 18% веса страницы. Из тайминга загрузки видно, что preload стоит
не на всех:

| Файл | Вес | Загрузка |
|---|---|---|
| `3e8ab5100a4aa694-s.p.woff2` | 50 КБ | 264 → 526 мс (preload) |
| `1f3fe8c6df3d47c1-s.woff2` | **95 КБ** | 699 → 833 мс |
| `e4af272ccee01ff0-s.woff2` | 47 КБ | 555 → 655 мс |

Два файла обнаруживаются поздно (555 и 699 мс) — значит они не в preload, в `<head>`
я видел только два `rel=preload as=font`. А 95 КБ для одного woff2 говорит о том, что
шрифт не сабсетнут: для русского сайта достаточно кириллицы + latin, это обычно 20–35 КБ.

Что сделать: сабсетнуть под кириллицу (`next/font` умеет через `subsets`), сократить
число начертаний, добавить preload оставшимся критическим.

## Что НЕ является проблемой

Чтобы не тратить время впустую:

- **Картинки.** 65 КБ на 5 запросов, WebP, `fetchPriority="high"` и `preload` на
  LCP-кандидате, корректные `sizes`, lazy ниже фолда. Сделано правильно.
- **CLS.** Ноль на всех восьми замерах.
- **Главный поток.** TBT 0–20 мс, bootup 0,2 с, main-thread work 0,7 с.
- **Сервер.** Root document 30 мс, TTFB 67–116 мс, `x-nextjs-cache: HIT`.
- **Третьи стороны.** Ноль запросов. Ни аналитики-тяжеловесов, ни виджетов.
- **Кеширование.** `max-age=31536000` на иммутабельной статике.

## Оговорка

Полевых CWV нет и не будет, пока нет трафика — CrUX формирует выборку только при
достаточном числе визитов. Поэтому:

- Сейчас ориентируемся на лабораторные цифры.
- После роста трафика (фаза A в `ACTION-PLAN.md`) полевые данные появятся сами, и их
  надо будет переснять: `GOOGLE_API_KEY` уже настроен, команда та же.

  включить его на
  `console.developers.google.com/apis/api/chromeuxreport.googleapis.com/overview?project=860353663714`.
  PageSpeed Insights API работает.
